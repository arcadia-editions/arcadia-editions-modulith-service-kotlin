# P-06 Payment authorized after the reservation expired

status: accepted A + B (query timer)
found by: S1 review (claude-opus), recorded by the orchestrator, 2026-11-13
flow: place-order-flow
blocks: none today (S8 flow test T-32 may hit it)

## Problem
The ZFL races two branches with no rule for who wins:
[place-order-flow.zfl:230-240](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L230) (ReservationExpired
10 minutes after OrderCreated, "unless payment authorized") and the authorization path (`PaymentAuthorized > confirmOrder`).

- If the release wins, `StockReleased > cancelOrder` cancels the order. A `PaymentAuthorized` arriving later finds the
  Order `CANCELLED`; `confirmOrder` throws `InvalidStateTransitionException`, so the event publication is retried with
  no end, and the authorized payment is never voided.
- If the expiry job releases between `PaymentAuthorized` and `confirmOrder`, `confirmStockReservation` returns silently
  over `RELEASED` reservations and the Order is `CONFIRMED` with no stock behind it.

The timer has no model input that says "payment authorized" (the job only sees reservation status), and no command
compensates an authorization that arrives for a cancelled order.

## Evidence
[review-S1.md](../../.zenwave/handoff/place-order-flow/reports/review-S1.md) (NOTE T-09):
`OrdersCheckoutServiceImpl.kt:88-99`, `InventoryServiceImpl.kt:133-136`.

## Options
- A: on `PaymentAuthorized` for a `CANCELLED` order, `confirmOrder` does nothing and emits a new event (e.g.
  `OrderConfirmationRejected`) that `voidPayment` listens to; `confirmStockReservation` fails (or reports) when the
  reservations are not `RESERVED`, so the order is not confirmed. Changes: ZFL branch, ZDL event + listener.
- B: the expiry job skips orders whose payment is authorized (asks payments in-process, or inventory keeps a
  "payment authorized" mark set by a `PaymentAuthorized` listener). Changes: ZDL listener on inventory; ZFL wording.
- C: accept the race; `confirmOrder` on `CANCELLED` is a logged no-op, and a person voids by hand. Changes: code only.

Recommendation: A. It closes both holes with the flow's own compensation (void), no cross-module query.

## Decision
A and B, decided by the person on 2026-11-17 (T1, the query timer). Changes in the models on branch `fix/payment-reauthorize-transitions` (arcadia-editions-modulith-api, arcadia-editions-architecture):
- B: the timer runs a new `expireReservation` in inventory, which calls the read-only `getPaymentStatus` in payments and releases the
  RESERVED lines (`RESERVATION_EXPIRED`) only on `NO_PAYMENT`; on `STARTED` payment owns the end. `releaseStock` no longer has the `@timer`.
  `authorizePayment` commits `AUTHORIZATION_REQUESTED` before the processor call, so a call in flight counts as started.
- A: `confirmOrder` emits `OrderConfirmationRejected` (reason `ORDER_CANCELLED` or `STOCK_NOT_HELD`) instead of confirming, on a
  `CANCELLED` order or when `confirmStockReservation` answers `NOT_HELD`; `voidPayment` listens to it (not to `OrderCancelled`: under T1 a cancellation never finds a hold, and it made the flow loop).
- No-ops so each path cancels the order once: `voidPayment` with nothing to void, `releaseStock` on RELEASED, `cancelOrder` on CANCELLED.
New baseline follows; the skipped race in `PlaceOrderFlowReservationExpiredIntegrationTest` gets scenarios.
