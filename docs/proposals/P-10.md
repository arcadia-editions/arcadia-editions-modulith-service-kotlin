# P-10 No failureReason code for a processor call that throws

status: open
found by: review of slice S1 (.zenwave/handoff/place-order-flow/reports/review-S1.md), 2026-11-17
flow: place-order-flow
blocks: T-75

## Problem
Since T-52, `authorizePayment` (and `reauthorizePayment`, T-57) commits `AUTHORIZATION_REQUESTED` before the processor
call. When the processor answers within 30 s by throwing (not a timeout), the exception is rethrown: the outcome is
never saved, no event is emitted, and a redelivery of the event is a no-op (status is not FAILED). The Payment stays
`AUTHORIZATION_REQUESTED` for good, `getPaymentStatus` answers STARTED, `expireReservation` does not release, and the
order never ends.

The ZFL is clear on the outcome: "a failure means a technical error on our side or the processor's, which we will
retry" ([place-order-flow.zfl:111-112](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L111)),
so a throwing processor is `FAILED` + `PaymentFailed`. What is missing is its `failureReason`: assumption A-06 of the
test data (`data.sql` header) lists the codes `card_declined, processor_timeout, capture_window_closed,
fulfillment_failed, warehouse_damage`, none for a processor error. The codes are not in the models.

## Evidence
- `PaymentsProcessingServiceImpl.callProcessor`: `ExecutionException` is rethrown; `TimeoutException` maps to
  `failed(processor_timeout)`.
- `FakePaymentProcessor` (`pm_card_processorNoAnswer`) throws when released; the S1 review saw
  `PlaceOrderFlowReservationExpiredIntegrationTest` leave a Payment row behind.

## Options
- **A.** Add `processor_error` to A-06 (a one-line change of the data.sql header, by the person); a throwing
  processor ends `FAILED` with `failureReason = processor_error`, retried like any failure.
- **B.** Reuse `processor_timeout` for any technical failure of the call. No test data change; the reason is less
  precise (support cannot tell a hang from an error).
- **C.** Put the code in the model (e.g. an enum `PaymentFailureReason` in the payments ZDL) and regenerate (HITL).

## Recommendation
A: the smallest honest change; B loses information, C is a regeneration for one string.
