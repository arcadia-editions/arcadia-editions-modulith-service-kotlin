# P-11 reauthorizePayment has no in-flight state in the ZDL

status: open
found by: review of slice S2 (.zenwave/handoff/place-order-flow/reports/review-S2.md), 2026-11-18
flow: place-order-flow
blocks: none (the code follows option A, as the board asked for T-57)

## Problem
`authorizePayment` declares its in-flight state: it commits `AUTHORIZATION_REQUESTED` before the processor call, so a
call in flight counts as started for `getPaymentStatus` (P-02,
[payments-processing-domain-model.zdl:119-128](../../../arcadia-editions-modulith-api/payments-processing-domain-model.zdl#L119)).
`reauthorizePayment` does the same in the code (T-57, as the board said: "commit AUTHORIZATION_REQUESTED before the
processor call (as T-52)"), but its transition says only `from: FAILED, to: [AUTHORIZED, DECLINED, FAILED]`
([:130-136](../../../arcadia-editions-modulith-api/payments-processing-domain-model.zdl#L130)). The model and the code
disagree on the states a Payment passes through during a retry.

## Evidence
- `PaymentsProcessingServiceImpl.reauthorizePayment`: REQUIRES_NEW block sets `AUTHORIZATION_REQUESTED`,
  `attemptCount + 1`.
- `PlaceOrderFlowRetry*IntegrationTest` (T-59) assert `AUTHORIZATION_REQUESTED` with the attempt count while each call is
  in flight.

## Options
- **A.** Add the in-flight state to `reauthorizePayment`: `@transition(from: FAILED, to: [AUTHORIZATION_REQUESTED])`
  and the outcomes as for `authorizePayment` (the P-02 shape). Matches the code and the tests; a retry in flight also
  counts as started for the reservation timer.
- **B.** Keep the ZDL: the Payment stays `FAILED` during the call and only `attemptCount + 1` is committed first. The
  code and T-59 change; `getPaymentStatus` still answers STARTED (any Payment exists).

## Recommendation
A: one shape for every authorization attempt, no code change; a ZDL edit and a regeneration check (HITL).
