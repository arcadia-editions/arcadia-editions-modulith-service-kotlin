# P-04 Spring Modulith module boundaries the generated layout does not respect

status: open
found by: T-02 (implementer claude-sonnet, checked by the orchestrator), 2026-11-12
flow: place-order-flow
blocks: none (T-02 tolerates these findings explicitly in `ArchitectureTest.isKnown`)

## Problem
`ApplicationModules.of(Application).detectViolations()` reports three kinds of findings that the code generated
from `zenwave-scripts.zw` produces by design, and that no task can fix without changing the generated layout:

1. **Module cycles through event types.** Each producer module owns its event classes (e.g.
   `orders.checkout.core.domain.events.OrderCreated`), and each consumer's `@listener` imports them. The flow's
   choreography makes the dependencies circular: orders -> payments (`PaymentAuthorized`), payments -> orders
   (`OrderCreated`), and catalog -> payments -> fulfillment/orders -> catalog.
2. **`common.mappers.BaseMapper` is not exposed.** Every module's MapStruct mapper extends it, and `common` does
   not declare it in a named interface.
3. **Module granularity.** Modulith detects the top-level packages `catalog` and `notifications` as modules, so
   `catalog.inventory` and `catalog.products` are one module and their boundary is not checked. The root
   `ModuleMetadata.kt` declares "Payments Processing" on the root package.

## Evidence
T-02's run of the old rules: 47 onion violations, all cross-module listener deps on `orders.checkout` events. The new
`ArchitectureTest.applicationModulesAreValid` passes only because it skips messages starting with
"Cycle detected" (so a new cycle would also pass), the `BaseMapper` message, and messages within one top-level
package.

## Options
- A: accept the cycles as the cost of event choreography in a modulith. Keep the tolerance but list the expected
  module pairs in it, so a new cycle fails. Expose `BaseMapper` (`@NamedInterface` on `common.mappers`) and
  declare `catalog.inventory`, `catalog.products`, `notifications.consumer` as modules (`@ApplicationModule` /
  `package-info`, or `@Modulithic(sharedModules = ["common"])` with the detection strategy that uses explicit
  annotations). Changes: code and `ModuleMetadata`; no model change.
- B: move the published event types into an API package per module (e.g. `<module>.events`, `@NamedInterface`)
  and let Modulith allow event-type dependencies. Cycles stay at the type level. Changes: the generator layout in
  `zenwave-scripts.zw`, regenerate.
- C: move every integration event into a shared events module (`common.events`). Cycles disappear. Changes: the
  generator layout, regenerate; breaks the producer-owns-its-events convention.

Recommendation: A now (no regeneration, tightens the test), B when the generator layout is revisited.
